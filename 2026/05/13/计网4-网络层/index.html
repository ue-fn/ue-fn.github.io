数据平面

Network Layer Functions

网络层：把传输层的段，从发送主机送到接收主机

发送端：封装成数据包（ip包），加上ip头，交给数据链路层发送

接收端：把收到的ip报解封装，取出字段交给运输层

协议在每一台主机和路由器生效

路由器决定如何转发

两大核心功能：

  • 数据平面：路由器收到包后，从输入端口移到指定的输出端口。只在单个节点（路由器）上执行，还包含错误处理、排队和调度。
  • 控制平面：决定数据包从源主机到目的主机，要经过哪些路由器、走哪条路径。由路由算法计算出 “从源到目的的最短 / 最优路径”，生成路由表。

Routers

互联网和路由器

边缘层：

用户侧边缘：比如图里的home, small business（家庭 / 小企业网络）、UMICH（密歇根大学）、NYU（纽约大学）、BBN（企业网）。这些网络的路由器，直接为终端用户提供接入服务，通常处理的用户流量更复杂，比如家庭宽带、校园网、企业内网

ISP 边缘（edge ISP）：运营商的接入路由器，负责把用户网络接入到运营商骨干网。

核心层就是运营商的骨干网络，比如图里的AT&T骨干网，核心路由器之间用高速线路互联，只负责高速转发数据，不直接和用户打交道。

核心层：

NAT：Network Address Translation

充当防火墙，隐藏内部ip地址，允许组织使用更多内网地址

三种NAT：

  • 静态NAT：一个私网ip绑定公网ip
  • 动态NAT，路由器有一批ip池，根据需要来提供私网ip
  • 网络地址端口转换：内网设备用同一个公网ip

NAT转换表：传输层协议-LAN端-WAN端-目的WAN端

IPV6

ipv4枯竭了快

ipv的新头部转发更快，原生支持服务质量，不再需要路由器的分片工作，新地址模式：

ipv6头部

version：4位（6）

traffic class流类别：标记优先级（QoS）

  • 上层协议（tcp，udp）可以设置它的值
  • 值是可变的
  • 上层协议不能假设它的值不变

flow label：属于同一个应用会话的所有数据包打上相同的 20 位数字

  • 只看这个标签，就能快速识别出它属于哪个流，直接套用预先设置好的转发规则，不用再解析复杂的五元组。

payload length：数据+所有扩展头部

next header：确定下一个字段的类型

ipv6对比ipv4的优势

  • 扩展编址能力：32->128位，组播机制支持更大范围一对多通信，任播支持（一个地址可以分配给多个节点，数据包会被路由到 “最近” 的那个节点），地址自动配置
  • 改进选项机制：扩展首部分离，中间路由器不处理大部分扩展首部，更容易扩展新选项，移除了首部校验和。支持除了 “尽力而为” 之外的 QoS 处理，比如给实时视频、语音通话提供低延迟、低丢包的保障，这是 IPv4 很难做到的。
  • 资源分配与 QoS 支持：用 Traffic Class 标记数据包的优先级和服务等级，用 Flow Label 把同一个流的数据包分组，路由器可以根据流标签快速识别流，统一处理
  • 更高效健壮的移动性，更强的安全性

ipv4适配ipv6

  1. 双栈策略：同时安装 IPv4 和 IPv6 两套协议栈

    部分字段（flow）直接丢失

  2. 隧道技术：制造了一个全新的 IPv4 大信封（IPv4 Header） 。然后把整个完整的 IPv6 数据包，当成普通的 Payload（数据载荷），硬塞进这个 IPv4 信封里

    但是效率很低

通用转发与软件定义网络（SDN）

通用转发：匹配+动作。当一个数据包到达路由器时，硬件去匹配（Match）**数据包首部里的特定比特（Bit）位，一旦对上了，就立刻执行对应的**动作

  • 基于目的地转发：
  • 通用转发模式：
    • 数据包首部里的许多个字段都可以共同组合起来，决定最终要采取的动作
    • 动作类型多，除了转发还能丢，复制，修改报头，记录日志

流表抽象：

  • 流的本质，就是由一组特定的“首部字段的值”定义出来的同一批数据包集合（涵盖链路层、网络层和传输层）
  • 简单的 packet 处理规则
    • 匹配项，动作，优先级（防止冲突），计数器

Routing protocols

找到一条好路径。

路径：指分组从源主机到目的主机所经历的路由器序列

好：least cost，快，拥堵最少

图的抽象：link cost

路由选择算法的分类：

​ 全局

静态 动态

​ 分散

Dijkstra 链路状态路由算法

centralized：每台路由器把自己和邻居的之恋情况打包“链路状态广播”给全网广播

iterative（迭代）：经过k次循环迭代，算法已经保证确定了前往k个目的节点的最短路径

问题：路由振荡 ：所有路由器同时运行路由算法，导致堵塞

Bellman-Ford 距离向量算法

$$D_x(y) = \min_v { c_{x,v} + D_v(y) }$$

（到目标的最短具体等于最短的邻居+邻居的最短距离）

当自己的D（v）变化后，通知邻居

每个节点根据邻居的一整张dv表更新自己的dv

Distance Vector 不是一下子让全网都知道信息，而是信息一跳一跳扩散出去

good news travels fast，只要更新就好

bad news travels slow导致“数到无穷”问题

Intra-ISP routing: OSPF

目前研究路由问题理想化：

  • 假设路由器都一样，所有路由器都参与同一套路由

问题：规模太大，管理自治性

互联网实现可扩展路由的方法：把路由器聚合成一些区域：自治系统AS

同一个 AS 内部路由器之间的路由：intra-AS routing

  • 相同AS的所有路由器必须运行同一种 intra-domain protocol）
  • 不同AS可以不同
  • gateway router，网关路由器，位于自己 AS 的边缘，并且有链路连接到其他 AS 的路由器。
  • 网关既做 AS 间路由，也做 AS 内部路由

互相连接的自治系统

  • 转发表由 AS 内部路由算法和 AS 间路由算法共同配置。
  • 对于 AS 内部目的地，转发表项由 intra-AS routing 决定。
  • 对于 AS 外部目的地，转发表项由 inter-AS 和 intra-AS 共同决定。

常见AS内部路由：OSPF：Open Shortest Path First

  • 公开可用

  • 经典链路状态协议

    • 每个路由器把 OSPF 链路状态通告泛洪给整个 AS 内的所有其他路由器

      （路由器的邻居，cost多少）

      OSPF 报文直接承载在 IP 上，而不是用 TCP 或 UDP

    • 链路 cost 可以基于多种指标，比如带宽、延迟

    • 每个路由器拥有完整拓扑，并用 Dijkstra 算法计算转发表。

  • 安全：所有 OSPF 消息都经过认证，用来防止恶意入侵

层次化 OSPF

  • 两级层次结构：本地区域和骨干区域。
  • 链路状态通告只在本 area 内泛洪，或者只在 backbone 内泛洪。
  • 每个节点知道自己所在 area 的详细拓扑；对于其他区域的目的地，只知道到达方向。

本地路由器：
只在本 area 内泛洪链路状态；
计算本 area 内部路由；
如果包要去 area 外部，就通过 area border router 转发。

area border router：区域边界路由器

：区域边界路由器会“汇总”到自己 area 内目的地的距离，并把这些信息通告到 backbone

backbone router：骨干路由器运行限制在 backbone 内的 OSPF

boundary router：AS 边界路由器：连接到其他 AS

Routing among ISPs: BGP

前面的是在说，自己网络里怎么走

BGP 是事实上的跨域路由协议（AS间路由），是把整个互联网粘在一起的胶水。

BGP 允许一个子网向互联网其他地方宣布：我在这里，我能到这些地方。

BGP提供：

  • 通过 eBGP，从邻居 AS 获得目的网络的可达性信息
  • 根据可达性信息和策略，决定到其他网络的路由
  • 通过 iBGP，把可达性信息传播给本 AS 内部所有路由器
  • 向邻居网络通告目的网络的可达性信息

两个 BGP 路由器（作为 peers），通过一条长期 TCP 连接交换 BGP 消息。

  • 信息：打开连接，
    • 并认证发送方 BGP 路由器
    • UPDATE：通告新路径，或撤销旧路径
    • 如果很长时间没有新的 UPDATE，双方也要定期发 ACKs
    • 报告错误，也可以用于关闭连接

向对方通告到不同目标网络前缀的路径。BGP is a “path vector” protocol)

  • 路径属性，BGP路由：

    • BGP 通告出去的一条路由，由“前缀”和“属性”组成
    • 两个重要属性：
      • AS-PATH：这条通告经过了哪些 AS。
      • NEXT-HOP：指明通向下一个 AS 的具体路由器

  • 网关路由器收到路由通告后，会使用 import policy 决定接受还是拒绝这条路径。

    （比如不经过y）

    AS 的策略也会决定是否把这条路径继续通告给其他邻居 AS

Hot potato routing：倾向于更少的AS内开销，AS间不用担心

ISP （互联网服务提供商（中移动，电信，，））通常只愿意转发“和自己客户有关”的流量，不愿意免费帮两个别的 ISP 之间搬运流量。

  • x 不会向 B 宣告“我这里能到 C”

BGP路径优先级：

  1. policy
  2. AS间
  3. AS内
  4. 其它

为什么？

  • 政策，inter-AS往往是不同组织间的
  • 互联网太大，分层改善路由
  • AS 内部更关注性能，AS 之间策略压过性能

SDN control plane

历史上的采用的是 分布式、逐路由器的控制方式，

传统网络的控制方式：每台路由器自己都有一个控制平面，自己参与计算转发表大约从

2005 年左右，大家重新开始认真思考网络控制平面应该怎么设计。

让底层设备主要负责转发，把控制逻辑拿出来，由一个逻辑集中的 controller 统一计算和下发转发表。

更容易管理、更容易编程、更开放

从：垂直整合的、封闭的、私有的、创新慢的

到：水平分层的、接口开放的、创新快的、产业巨大的

传统路由：管理员不能直接指定路径，只能调链路权重，让分布式路由算法“碰巧”算出想要的路径，不会细分“你是什么类型的流量”

SDN：

  • 广义的、基于流的转发（把“满足某组条件的包”看成一条 flow）
  • 控制平面和数据平面分离
  • 控制功能移到交换机外部（ 不只是算最短路，还可以支撑很多网络控制功能
  • 可编程的控制应用

数据平面switches：

  • 是“快、简单、便宜/通用”的转发设备
  • flow table 由 controller 计算并安装
  • API 定义“哪些东西可以被控制”
  • switch 和 controller 之间还需要通信协议

SDN controller (network OS):

  • 维护网络状态（掌握一个更全局的网络视图）
  • 上层应用通过 northbound API 调用 controller 的能力
  • 向下控制交换机
  • controller 物理上可以是分布式系统

network-control apps:

  • 是控制逻辑的大脑，controller 给应用提供底层服务：路由，访问权限控制，负载均衡
  • 解捆绑：routing app、firewall app、load balancing app 不一定必须由交换机厂商提供。第三方、研究者、管理员自己都可以写。

Components of SDN controller

  • 给上层应用的接口层。全网状态管理。和底层设备通信

OpenFlow（在 controller 和 switch 之间）

  • 通信协议：tcp
  • 三类消息：
    • controller 主动发给 switch，
      • 查询features
      • 查询配置参数
      • modify-state：添加，删除，修改 flow entry
      • 让某个 switch 把一个指定的包从某个端口发出去
    • 异步消息（switch主动上报），
      • switch 收到一个包，但 flow table 里没有匹配项。
      • 告知某条 flow table 项已经被删除
      • 告知我的某个端口状态改变
    • 对称消息（ controller 和 switch 都可以发，不严格分上下方向）
  • 和 OpenFlow API 不一样。OpenFlow API 偏向”能表达控制什么规则“。它是controller 和 switch 怎么把这些规则传过去。

实例：

  1. s1 发现链路故障，上报 controller
  2. controller 更新自己的网络状态
  3. Dijkstra 路由应用被调用
  4. 路由应用读取全网图，重新算路
  5. 路由应用会和 controller 里的 flow-table-computation 组件交互，计算出需要的新 flow tables
  6. controller 把这些具体规则下发给相关交换机

ONOS：一种具体的 SDN controller控制器平台

SDN的挑战：

  • 控制平面一旦出问题，影响范围可能很大
    • SDN 控制平面要借助可靠分布式系统理论来抵抗故障
    • 可靠性和安全性不能等系统做好了以后再补丁式添加，而要从第一天设计时就考虑进去。
  • 未来网络会有很多特殊任务需求，不是“能转发 IP 包”就够了
  • SDN 在单个组织内部很有优势，但要“统一控制整个 Internet”，基本不是这么简单
  • SDN 对 5G 网络很重要

SDN与传统网络协议的未来

  • 由 SDN 计算转发表 vs. 由路由器自己计算转发表
  • 人们甚至可以设想一种由 SDN 计算的拥塞控制。controller 根据路由器上报给 controller 的拥塞程度，来设置发送方的发送速率

ICMP：Internet Control Message Protocol

ICMP 被主机和路由器用来交流网络层信息，比如报错：主机不可达、网络不可达、端口不可达、协议不可达；也可以做 echo request/reply，也就是 ping 用的东西。

ICMP 属于网络层，逻辑上在 IP 上面一点，但 ICMP 报文是装在 IP 数据报里传输的。

ICMP message包括：type | code | 引发错误的原始 IP 数据报的前8字节

（前8字节通常足够包含 TCP/UDP 头部的关键开头字段，尤其是端口号，用于判断是哪一个包出错）

源主机这一侧的人或程序想知道路径：traceroute故意让包死在第 1 个、第 2 个、第 3 个路由器那里”，然后让这些路由器回信，从而知道路径的。

Network management, configuration

一个大网络里有成千上万台路由器、交换机、防火墙、服务器，网络管理员到底怎么知道它们的状态？又怎么批量修改它们的配置？

网络管理 = 看网络状态 + 查网络问题 + 改网络配置 + 保证网络按预期运行

网络管理系统里有哪些角色：

  • 被管理的设备
  • Managing server有网络管理员参与的应用
  • network management protocol 用于管理服务器查询、配置、管理设备，也用于设备向管理服务器报告数据和事件
  • 可被管理的数据（data 包括设备状态、配置数据、运行数据、统计数据）

方法：

  • CLI：直接登录设备敲命令
  • SNMP/MIB：查询和设置设备数据
    • 两种传递 MIB 信息和命令的方式：request/response mode（ types 0-3） 和 trap mode（ types 4）
    • MIB：是 managed device 的 operational data 和一些 configuration data，这些数据被 gathered into device MIB module
    • SMI 是一种数据定义语言，规定 MIB 对象应该怎么定义
  • NETCONF/YANG：更抽象、更整体的配置管理
    • 目标：主动地、全网范围地管理和配置设备
    • 它运行在 managing server 和 managed network devices 之间。像调用远程设备上的函数一样，让设备执行某个操作。
