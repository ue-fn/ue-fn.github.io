应用层概述

  • 应用：不同设备上的应用进程，通过交换消息来完成功能
  • 应用层协议：应用的通信规则
    • 定义应用交换什么样的信息
      • 格式：比如http里有get，post，还有200 ok，404 not found
      • 字段分隔和排版：比如http请求头：GET /index.html HTTP/1.1 Host: www.baidu.com User-Agent: Chrome/120.0.0.0
      • 字段的语义
    • 定义收到信息后的动作

行话：

  • 进程

    • 同一台主机的进程用进程间通信（ipc）对话
    • 不同主机需要用应用程协议通信

  • 用户代理

    • 在用户/应用 和 底层网络之间当接口，一边对接你的操作界面，一边实现应用层协议。
    • 比如说浏览器，邮件服务器，b站客户端

两种主流架构

  • Client-Server Paradigm（cs）
    • 客户端：按需启动，主动通信，动态ip地址
    • 服务器：always-on，回复相应，固定ip
  • Peer-to-Peer Paradigm（p2p）
    • no always-on server
    • 端系统直接通信
    • 双向服务角色
    • 节点动态性
    • （这玩意现在是不是不常见了？）
  • 混合架构
    • skype（网络电话）：中心化服务器（负责帮助client找到对方ip），p2p核心，只在通话建立的瞬间工作，连接完成后，服务器完全退出
    • instant messaging(即时通讯)：中心化服务

DNS(Domain Name Service)

  • function：把域名转化成ip地址
  • DNS
    • 分布式数据库：分布式、分层级的数据库，由全球无数个「域名服务器（name server）」组成，不是一个中心化的大服务器
    • 应用层协议：主机和域名服务器之间通过DNS协议通信，完成域名解析
    • 负载均衡：一个域名可以对应多个ip地址

为什么dns不能用中心化架构？

  • 单点故障：一旦它宕机，整个互联网直接瘫痪
  • 流量爆炸
  • 延迟过高
  • 维护灾难

设计核心目标

  • 唯一性，无命名冲突
  • 可扩展性：支持频繁的新增 / 修改
  • 分布式，自治管理：
    • 自由修改自己服务器的域名 / IP
    • 不需要跟踪所有人的域名更新，只需要维护自己的层级
  • 高可用性
  • 查询速度快
  • 不要求完美一致性

如何做到Scalable？

  • 划分命名空间
  • 分布式管理每个分区
  • 分布式解析每个分区
  • 怎么划分？树状结构。每个层级只负责自己的范围，完全自治。每台服务器只存一小块数据
    • 根域管理顶级域（.com/.cn/.edu）的分配；
      • Root Name Servers。返回 顶级域服务器 的 IP 地址映射
    • 顶级域管理二级域（nju.edu.cn/baidu.com）的分配；
      • TLD Servers（顶级域服务器）它手里有每个二级域（如 baidu.com、nju.edu.cn）的权威服务器地址。
    • 二级域管理自己的三级域（cs.nju.edu.cn）；
      • Authoritative DNS servers:
      • 本地 → 根 → TLD → 权威 → 返回 IP
    • 本地DNS
      • 不严格属于DNS 的层级树结构，本地 DNS 是用户侧的代理 / 缓存节点
      • 本地缓存&代理转发

DNS Name Resolution Example（DNS 解析完整示例）

请求方：Bob，主机cis.poly.edu

目标：查询gaia.cs.umass.edu的 IP 地址

主机向本地DNS dns.pply.edu发送查询请求

缓存没命中，向根DNS请求，返回下一个地址 -> 向TLD服务器 -> 查权威服务器 -> 本地 DNS→主机

Host-Server: recursive query（主机→服务器：递归查询）

Server-Server: iterative query（服务器→服务器：迭代查询）

DNS Records（DNS 资源记录）

RR format: (name, value, type, ttl)

域名，值，类型（决定值的含义），生存时间

DNS protocol

DNS 的查询（Query）和响应（Reply）报文使用完全相同的格式

• Header: identifier（标识符）, flags, etc.

• Plus resource records

• See text/section for details

默认使用 UDP 53 号端口（支持 TCP 53 号端口）

**Reliability（可靠性保障机制）**主从复制的冗余服务器，默认使用 UDP 协议，超时自动切换，统一查询标识符

快速查找：

缓存是分层级的，从浏览器缓存→操作系统缓存→本地 DNS 缓存→根 / TLD 服务器缓存，多层缓存共同加速解析。

Electronic Mail

user agent:

  • 收发邮件。读邮件
  • 只是 “纯客户端”，不负责存储邮件

mail server：

  • 邮箱：存放用户邮件
  • 消息队列：存放用户待发送的邮件
  • SMTP：服务器之间发送邮件的标准协议

邮箱投递三阶段：

  1. 本地提交 (Local User Agent → Local SMTP Server)

    User Agent：充当 SMTP 客户端 (Client)。

    Local Mail Server：充当 SMTP 服务器 (Server)。

  2. 远程中继 (Local Server → Remote SMTP Server)

    Local server acts as SMTP client now

  3. 远程访问 (Remote User Agent → Remote Server）

    收件人的 User Agent 连接远程服务器的 Mailbox

SMTP（推）

  • 协议基础（RFC 821）
    • 基于 TCP，默认端口 25
    • 客户端→服务器直接推送邮件
    • 仅读取邮件「信封」信息。不定义邮件内容格式。Messages must be in 7-bit ASCII
    • 每一跳服务器会在邮件头添加Received日志，记录邮件传输路径
  • 传输流程
    • Handshaking (greeting)：
    • Transfer of mails data
    • Close connection
  • reliability
    • 基础可靠性：依赖 TCP
    • 不保证恢复丢失邮件
    • 无端到端确认
    • 错误指示不保证送达
    • Generally considered reliable

邮件的结构

  • Header lines, e.g.

    – To: Alice@sina.com

    – From: Bob@gmail.com

    – Subject: Dinner tonight

  • Body

  • 邮件地址格式为：邮箱名@SMTP服务器域名

Mail Access Protocols

  • SMTP：发邮件协议
  • Mail access protocol:收邮件协议
  • POP：「邮局模式」身份认证+下载邮件
  • IMAP：更丰富的特性，支持在服务器上操作邮件
  • HTTP：网页邮箱专用

POP3/IMAP (拉取)

  • 用户通过接收协议从服务器将邮件“拉”取到本地
  • POP3（Post Office Protocol Version 3）
    • 登录授权阶段：
      • 客户端发命令：账密
      • 服务器回应：+OK -ERR
    • 事务操作阶段
      • list：列出所有邮件编号和大小
      • retr：按编号下载指定邮件
      • dele：标记指定邮件为删除
      • quit：退出
    • 默认下载并删除（不支持多设备查看），支持下载并保留（但是状态不同步比如已读）
    • 无协议状态
  • IMAP（Internet Mail Access Protocol）
    • 邮件始终存在服务器，支持多设备同步（时）访问
    • 状态协议，多设备一致
    • 支持部分下载
    • 支持文件夹

File Transfer Protocol (FTP)

核心功能：用于在本地文件系统与远程主机文件系统之间传输文件 。

架构：采用典型的 Client/Server 模型，由客户端主动发起传输请求 。

解决异构性：它能处理不同操作系统和文件系统之间的差异 。

WWW and HTTP

web的核心组成

  • 基础设施

    • clients：用户和web交互的入口
    • servers：存储网页、数据、资源的后端设备（DNS, CDN, datacenters）

  • 内容层

    • URL：统一资源定位符
      • URL 是互联网上每一个资源（网页、图片、文件、接口）的唯一标识符
      • 标准格式<protocol>://<host>:<port>/<path>?query_string
      • host：资源所在服务器的域名或 IP 地址
      • post：服务器上对应服务的「入口编号」，不同端口对应不同服务
    • HTML：超文本标记语言，给网页排版

  • Protocol for exchanging information: HTTP

http核心特性：

  • 客户端 - 服务器架构：server在线，clients主动连接
  • 同步请求 - 应答协议：客户端发完请求后，必须等待服务器返回响应，才能进行下一次操作，基于TCP 协议传输，默认端口是80
    • Client-to-server communication
    • GET/HEAD POST POST PUT(更新资源) DELETE
    • 请求报文：
      • 请求行：<method> <resource> <protocol version>
      • e.g. GET /somedir/page.html HTTP/1.1
      • Header lines（请求头）请求行之后的多行键值对，用来传递客户端的附加信息、协商通信细节
      • Blank line（空行）
    • Server-to-client communication
    • Status line（状态行）：
      • HTTP/1.1 200 OK
      • HTTP 协议版本/：3 位数字状态码，用来表示请求的处理结果/状态码的文本描述，方便人类阅读
    • Response headers（响应头）
    • Blank line（空行）
    • Body（响应体，可选）
  • 无状态，服务器不存客户端状态
    • 优劣
  • ascii format

如何让无状态的协议有状态？cookie

  • 客户端状态维护
    • 服务器生成一个小数据（比如用户 ID、会话 ID），让浏览器（客户端）存在本地。
    • 浏览器后续给这个服务器发请求时，会自动把这个数据附在请求里发给服务器。
  • 可以做身份认证
  • cookie的应用
    • 价值：Authorization（身份授权）Shopping carts（购物车）Recommendations（个性化推荐 User session state (Web Email)（用户会话状态）
    • 风险：用户隐私，敏感信息，

web性能指标：

  • user：下载速度，高可用性
    • 下载速度不是低延迟（Improve networking protocols including HTTP, TCP, etc.）。
  • 内容提供者：让user开心，高性价比的基础设施 利用规模经济（效应
  • 网络：避免过载

缓存与复制

http性能：

现代网页痛点：

  • 绝大多数网页都包含多个资源对象
  • 原始（naive）的请求方式：性能灾难One item at a time：串行逐个请求资源
  • 每一个小资源都新建一个 TCP 连接

http请求响应时延的完整计算

  • RTT：一个小数据包从客户端发送到服务器，再返回客户端的总时间

    获取n个对象的时间

    小对象：传输时间远小于往返延迟 RTT

    • 一次一个：2n RTT（一次TCP握手，一次HTTP请求响应）
    • m个并发：2×⌈n/m⌉ RTT
    • 持久：（n+1）RTT（建立联系+n次http请求）
    • 流水线：2 RTT。同一个持久连接上，不用等前一个响应回来，就可以连续发送所有请求
    • 流水线 + 持久：2 RTT+ 1RTT

    大对象：延迟可以忽略，主要看带宽如何（F：单个文件大小 B：网络有效带宽）

    • 一次一个：nF/B
    • m个并发：[n/m]F/B
    • 流水线/持久：跟一次一个一样

CDN

缓存

  • 大家常访问的内容差不多，容重叠大就很有效

  • 客户端发请求时带上：If-modified-since: 时间

  • 服务器对比资源最后修改时间

  • 没改：返回304 Not Modified 改了：200 OK + 新内容

CDN

解决的问题：单服务器扛不住大文件实时传输，防 DDoS，降低用户访问延迟

做法：源服务器把内容复制到全球很多CDN节点，用户请求被DNS重定向到最优节点

核心技术：DNS重定向，URL重写，应用层覆盖网络（CDN节点之间相互调度）
